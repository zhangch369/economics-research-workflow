# Zhangchi 的经济学科研管理方式

先做一个改变：**以后每个重要结果，都绑定一个运行编号、一份分析数据版本和一张 AI 恢复卡。** 文件夹结构服务于这三个关联。

## 1. 数据按用途分层，按版本保存

|层级|保存内容|修改规则|最低验收|
|---|---|---|---|
|data_raw：原始/固定输入|来源原件、下载包、年报 PDF、API 原始响应、约定冻结快照|每次采集建新快照，不直接改原件|来源、获取时间、覆盖范围、文件清单与指纹|
|data_intermediate：中间数据|标准化、匹配、筛选、合并后的阶段数据|由明确代码生成；同一版本不被其他运行覆盖|唯一键、匹配率、重复、缺失、观测数变化|
|data_analysis：分析数据|变量处理和样本规则已经落实、供估计读取的数据|数据版本固定；改变规则产生新版本|单位、样本、变量时间、处理顺序与正式数据签名|
|outputs：结果证据|日志、估计、实际估计样本、表图、QA、环境和代码快照|每次运行独立留档，包括失败|退出状态、必需产物、独立 QA 与结果核对|

`analysis` 不等于所有模型的实际样本。控制变量缺失、固定效应单例剔除、估计器行为可能继续改变样本；每列保存键值和 `e(sample)`，同时保存估计结果。未估计、被省略、不可识别要有状态，不留一个无法解释的空白。

数据登记用 `DATA_REGISTRY.csv`：一个数据集一行，写清相对路径、生产程序、父数据、主键、单位、时间覆盖、零/缺失规则及公开限制。大批年报可按“一个批次＋分片清单”登记，避免手工为十万份文件维护表格。

原始数据再补来源元信息：提供方和查询条件、下载/采集日期、来源版本、权限/获取方式。首次冻结或转移时生成 SHA-256 清单；日常不反复扫描所有大型原始文件，只检查本次实际输入或已冻结快照。迁移到目标机器后验证收到的文件。

人工修改写成有主键的修订表，记录原值、新值、理由、证据和日期，再由 Stata 应用；不手工覆盖正式 `.dta`。年报 AI 分类同时保存文本版本、词表、prompt、模型标识、参数、原始响应和失败/重试状态。请求失败与“未采用 AI”不是同一个值。

## 2. 一条明确的生产链

```mermaid
flowchart LR
  A[来源原件与固定快照] --> B[Stata 清洗与合并]
  B --> C[保存中间数据]
  C --> D[Stata 构造分析数据]
  D --> E[逐列估计与实际样本]
  E --> F[独立 QA]
  F --> G[固定版本与论文表图]
  G --> H[Word / LaTeX / Beamer / PPT]
```

清洗、估计、QA 各自独立。主入口明确顺序，不按文件名字母顺序执行整个目录。耗时服务器阶段和本机分析之间用保存的数据版本交接，不依赖上次会话中的内存。

主回归、稳健性、探索各有 `spec_id` 和层级；禁止探索结果无说明地替换主结果。`SPECIFICATIONS.csv` 写清：分析单位、处理/对照、Y/X、变量时间、样本、固定效应、聚类、识别策略及限制。缩尾→取对数→求均值→差分并无通用顺序，必须逐规格记录用户实际指定的顺序。

对科技园，普通对照与 pseudo 对照分别登记；未核实的检查记录保留缺失，PPML 维持项目指定的 `sep(none)`。对 AI 长差分，同期指标、基期控制与端点变换分别记录。对贸易长均值/异质性，不混淆不同分类、固定效应与覆盖样本；JIE2022/CP2015 的公式核查、数据复现与均衡求解分别验收。

## 3. 每次运行就是一份可追溯记录

```text
outputs/
├── tables/02_main_regressions/main_table_demo_20261027_v01.doc
├── figures/02_main_regressions/main_figure_demo_20261027_v01.png
├── logs/02_main_regressions/analysis_demo_20261027_v01.log
├── estimates/、samples/、qa/         各按code模块分类、文件日期版次
├── provenance/                     对应版次来源快照
└── runs/demo/run_20261027_v01.json   运行记录与准确产物路径
```

运行记录回答：哪台机器、哪个代码版本、哪些输入、哪个任务/规格、何时开始结束、环境是什么、结果在哪里、为什么成功或失败。模板保留 Stata `about` 和 `which` 输出；正式项目还需固定 ado 依赖及报告工具版本。仅写 `version 18.0` 不能替代对用户扩展包、字体和外部软件的记录。

Stata 启动前将进程工作目录设为对应模块的 `outputs/logs/`，用绝对路径执行包装 do-file；业务路径统一由配置生成。失败日志保留在同一运行目录，不覆盖上一轮。突然断电或强制终止可能留下 `RUNNING`，应核查进程后补记为中断，不能据此当成成功。

内部成功判定由三项组成：程序结束正常、必需产物齐全、独立 QA 通过。QA 在 code/90_qa/，由启动器在生产入口之外调用。对外生产复现包排除内部 QA 和任务配置中的 QA 调用，明确记录 qa_status=NOT_RUN；生产链能够独立运行。真实项目的数值对照、全链数据重建和论文成品验收仍需逐项登记。

## 4. 本机与服务器搬家：只改机器配置

code、config、data_raw、data_intermediate、data_analysis 和其他功能目录在同一个项目根目录平级；根目录同时是 Git 根目录。原始和中间数据忽略，分析数据纳入 Git。机器配置分别填写 data_raw_root、data_intermediate_root、data_analysis_root；可指向对应挂载盘。业务脚本只使用这三个配置派生的路径，不写个人桌面路径或盘符。

1. 冻结待搬版本：记录代码提交/快照、数据清单、运行状态和已接受结果；暂停对同一数据版本的写入。
2. 传代码和所需数据版本：本机通常只需分析数据、估计所需中间输入和必要字典；全链重建才传完整原始快照。第一次传输不带删除选项，不用双向自动同步合并正在写入的 `.dta`。
3. 在目标机器填写机器配置，安装经登记的 Stata、ado 和其他工具；验证输入指纹与依赖。编译的扩展、求解器和字体需在目标系统检查。
4. 先跑合成示例，再跑一个指定正式任务；比较主键、样本、系数/协方差、标准误、观测数、聚类数、被省略项与成品。最后运行约定范围的完整入口。
5. 把目标机器的新运行目录带回，登记到版本/恢复卡；原版本保留。任务交接标明当前执行机器，避免两个机器覆盖同一可变目录。

每次独立构建使用新的日期版次文件；只重跑估计则显式引用已冻结的版本，不“自动寻找最新数据”。模板通过 `config/tasks.json` 登记输入，尚未提供自动缓存或断点续跑系统。

## 5. 可复现分清起点

|范围|起点 → 终点|应如何表述|
|---|---|---|
|结果复现|固定分析数据 → 估计、表图|本地结果复现通过|
|构建复现|原始/约定固定输入 → 分析数据 → 表图|指定输入快照下的构建复现通过|
|来源重采集|下载/爬取/API → 来源快照|采集流程已验证；动态网站/模型响应不保证逐条相同|
|跨机复现|相同登记输入和代码 → 目标机器输出|在具体系统、软件版本与容差下通过|

每个版本在清单中记录实际完成范围。输入不可公开时，保存准确获取流程、权限条件、可分享的派生数据和所有允许公开的代码；内部可复现和可公开发布是两件需要分别验收的事。

QA 不依赖“显著性一致”。先比较样本键与离散状态，再比较数值。容差在运行前登记，例如按项目数值尺度设绝对与相对阈值；不能为了掩盖差异临时放宽。随机任务固定种子、排序与并行设置；结构模型还比较收敛及均衡残差。二进制文件因保存时间不同导致哈希不同，不自动等同于数据值变化。

## 6. AI 接手与核心聊天恢复

规则唯一入口是 `AGENTS.md`，机器可读入口是 `project.json`，任务入口是 `config/tasks.json`。不同客户端的简短引导文件都指向它们；避免为每个 AI 单独维护一套互相矛盾的规则。没有自动读文件能力的 agent 使用 `ai_records/START_HERE.txt`。

核心聊天写入 `ai_records/YYYYMMDD_topic/`。关键原话、已接受决定、AI 建议、实际执行、未完成事项分开记录。恢复卡把代码、数据版本、运行目录、表图与写作版本连起来；本地副本优先，原生聊天链接辅助。

新 agent 不需要通读所有聊天：先用 INDEX 找相关任务，再看恢复卡和所指的真实文件。每次结束更新一份简洁状态；有规格/样本/版本决定时才追加核心记录，避免产生大量无价值摘要。

## 7. 写作与结果绑定

`writing/manuscript/word` 与 `writing/manuscript/latex` 放论文；`writing/presentations/beamer` 与 `writing/presentations/pptx` 放汇报。`writing/shared` 放引用库和导入的表图；`writing/releases` 保存里程碑成品。

写作版本登记哪个文件正在主编辑，图表登记来自哪次运行与哪个规格。导出时保存 `.docx/.tex/.pptx` 源文件和适用的 PDF，记录编译器与字体。不用“final_final”区分版本，用日期/版本编号和清单解释状态。

## 8. 清理、Git 与备份

每周五 17:00 同时检查清理与目录结构：输出放错位置、code 内出现数据/日志、未登记重复子项目、output/outputs/results 用途冲突。先读取各项目实际布局；已登记的模板、归档、正式子项目和运行快照不因嵌套自动判错。提醒给出具体路径、建议归位位置和一个可立即开始的动作。重要版本验收后也生成候选清单，不自动加第二个提醒。`CLEANUP.csv` 登记路径、体积、依据、生产代码、保留版本是否依赖、重建命令、确认记录和实际删除记录。

|文件类别|默认处理|
|---|---|
|原始数据、手工修订、模型原始响应、正式分析数据|保留来源快照与可恢复版本|
|正式运行日志、估计、实际样本、AI 恢复卡、写作定稿|作为证据保存，可转冷存储|
|可重建的中间产物、编译缓存、明确废弃的临时文件|确认没有保留版本依赖且重建代价可接受后，列入待删|
|Git 仓库与 worktree|检查未提交/未推送内容、分支与工作区用途；保留版本历史|

“可再生成”不自动等于“现在可删”：如果重建需数天、付费请求、已不可访问的输入或已删除代码，应保留或先补齐来源。用户确认不要的具体文件可以按清单删除；不再询问已确认范围，但存在新的下游依赖时先说明冲突。

Git 管理生产代码、内部 code/90_qa、文本与 data_analysis/ 中需保留的分析数据版本；data_raw/ 和 data_intermediate/ 用独立备份与清单，不同步 Git。Git 大小异常先辨认是大文件历史、正常对象还是闲置工作区；整理 worktree 优先使用管理工具。普通维护不需要删除 `.git`；历史重写、强制 prune 或抹掉仓库需单独授权。Git 状态干净也不能证明大型数据已备份。

重要版本至少有工作副本和另一设备/位置的恢复副本；定期选择一个版本测试恢复。若使用云同步，不把唯一同步副本当作独立备份。备份范围覆盖数据、代码、日志、核心聊天与写作；凭据单独管理。

## 9. 每天只维护这条短流程

1. **开始前约 2 分钟**：读 STATUS 和本次恢复卡，明确一个交付物、输入版本和验收标准。
2. **执行时自动留档**：使用登记入口，数据整理→估计→QA，所有记录进入本次运行目录。
3. **结束时约 3 分钟**：写已完成、证据、未完成和一个下一步；重要决定追加到恢复卡/决策记录。
4. **里程碑约 10–20 分钟，不含长运算**：验收表图与写作成品，登记固定版本，生成清理候选。

这些是管理动作的估计时间，实际回归、抓取和服务器重建时间由数据规模决定，单独记录实测耗时。

## 依据与适用范围

本目录分工、恢复卡、版本关联和执行约束是结合现有项目设计的工作约定。AEA 的数据代码政策要求提供足以支持复现的数据、变换和分析代码，并说明受限数据的获取方式；README 指南列出环境、运行说明及表图与程序映射。这里只借鉴这些要素，不声称模板已经通过期刊复现审查。[AEA 政策](https://www.aeaweb.org/journals/data/data-code-policy) · [README 与验证指南](https://aeadataeditor.github.io/aea-de-guidance/preparing-for-data-deposit.html)

Stata 官方文档说明批处理与日志行为、Windows 的工作目录设置和 do-file 版本控制；模板据此设置启动目录与机器参数。[macOS 批处理](https://www.stata.com/manuals/gsmb.pdf) · [Windows 批处理](https://www.stata.com/manuals/gswb.pdf) · [version](https://www.stata.com/manuals/pversion.pdf)

## 当前目录命名补充

management/ 是管理说明与登记；research_notes/ 是 AI 整理的 Markdown 思考报告；writing/ 是论文与正式汇报稿。code 参照NUSTP采用 00_setup→01_data_preparation（内分01_clean/02_build）→02_main_regressions→03_robustness→04_mechanisms→05_extensions；图表导出语句直接写在对应分析脚本中，生成文件保存到本次 outputs/ 下的 tables/ 或 figures/，不单设图表导出阶段。内部 code/90_qa 不进入对外复现包。阶段内文件也以数字开头，标明数据类型与用途。

## 服务器代码协作

涉及服务器代码时，本机修改后按 SERVER_SYNC.md 生成离线差异，获得 Zhangchi 对本次同步的同意后再连接/上传/修改服务器。服务器与本机采用相同扁平根目录，不增加 project 层。实际远端指纹和适用任务验证通过后才记录同步完成；只与旧快照一致不代表实时远端一致。

## 2026-10-27：任务化协作补充（当前规则）

执行较大任务先用 templates/TASK.md 绑定交付物、输入版本、依赖、文件所有权和验收。具体分工、两轮审查、状态与复用边界统一以 [AGENT_WORKFLOW.md](AGENT_WORKFLOW.md) 为准；新项目按 [NEW_PROJECT.md](NEW_PROJECT.md) 启动。

协调者统一维护共享登记和恢复索引；正文关键论断使用 CLAIMS.csv 接到 EXHIBITS.csv。自动化能力与未完成项以 AUTOMATION_ROADMAP.md 为准。原第3节的运行留档已由启动器支持；任务卡、状态汇总及论断登记目前由 agent/人工维护，不能称全自动。

输出分类细则见 [OUTPUT_LAYOUT.md](OUTPUT_LAYOUT.md)：所有语言统一使用 logs/tables/figures，日志与研究图表分开。

## 当前分类与命名规则

DATA_LAYOUT和OUTPUT_LAYOUT为当前有效布局：数据逐级镜像code；outputs类型优先；版本直接标文件名YYYYMMDD_vNN，不新建随机后缀目录。每次结束/每周检查提醒清理完全无用的临时txt和废弃产物，保留正式结果与复现依赖；旧的随机目录说明仅属于历史设计，不能用于新任务。
